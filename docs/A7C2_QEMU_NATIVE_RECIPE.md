# a7c2-re 的 QEMU 原生菜单配方 —— 对我们有什么可用

> 来源：`chocotan/a7c2-re`（A7C II，ILCE-7CM2），`report/2026-10-17-qemu-native-camera/`
> 本地 clone：`/root/fw/a7c2re`，HEAD `d0bc267`
> 记录时间：2026-11-05。本文只提炼**对本项目（ZV-E10 移植 ZV-1M2 新菜单）可用的部分**，
> 不复制其代码，不重新分发其资产。

---

## 0. 最重要的一句话

**他们不是靠"模拟 GPU"出画面的，是靠"用户态替身"出画面的。**

他们的显示链是 **原固件菜单 → 软件 GPE 执行绘图 → 有所有权保证的提交 → host 侧 ramfb**，
GPU 硬件从头到尾没有参与。这对我们意义重大：我们一直在
`sugilite` 驱动 / IRQ 76 / 寄存器状态机上死磕，而这条路**可能整条都是可以绕开的**。

---

## 1. 他们的八步，逐条对照我们的处境

| 步 | 他们做的 | 我们当前 |
|---|---|---|
| 1 | 让原内核可靠启动（固定 Image/DTB 装载、改 DTB `/chosen/bootargs`、保留内存预留、补 GIC/定时器） | ✅ 我们已做到（自建 `-M zve10`） |
| 2 | 让原应用进入可观测状态（初始化 IPC/Backup/DMM，缺失服务用限定替身） | 🟡 我们到 `Application_Start`，但 backup 队列无接收者 |
| 3 | **用原框架建立菜单**，而不是手工画：在受控时机调用原九参数入口 `0x1e78870`，把启动屏切为菜单 controller | ❌ **我们没做这一步** —— 我们一直在等引擎自己创建菜单 |
| 4 | **实现已核准的 Fill/精确 Copy**，再显式启用 Sprite、A8 字体、混合、tile/伸缩 | ❌ 我们没做 |
| 5 | **LZ77 用 CPU 解码**：31 次原 LZ77 调用因缺 `/dev/ldec` 全失败；用同格式 CPU 解码读原 UXC，经原位图锁写入 | ❌ 我们没做（我们树里有 `ldec` 节点但无驱动） |
| 6 | **恢复帧消费**：为缺席的 LIRO 接收任务提供 AP-only headless 端；1002→1003/1005 配对；提交 HOSDAP02 后通知完成 | ❌ 我们卡在这（我们的 ioctl 等完成位永不返回） |
| 7 | 把已提交像素交给 QEMU 真正显示：`ramfb-viewer` 校验容器后转 XRGB8888，走 **fw_cfg DMA / `etc/ramfb`** | ❌ 我们没做（我们用静态 FB 模型） |
| 8 | 再验收交互（原生按钮 → 私有通道 → 原输入队列 → 固件语义） | ⏸ 太早 |

**⇒ 我们的第 1、2 步和他们基本一致；第 3~7 步我们几乎一步都没做，
而是在第 6 步的"底层设备模型"里反复打转。**

## 2. 可复用的具体接口（他们公开的）

### 2.1 菜单入口（第 3 步的关键）
```
原九参数入口地址：0x1e78870
作用：把 308 启动屏一次切为 346 菜单 controller
保留：原析构、构造、init、请求泵
结果：请求泵自然创建 0x2ca / count44，之后发出菜单绘图请求
```
> ⚠️ 这是 **A7C II 的地址**。ZV-E10 / ZV-1M2 的对应入口需要自己定位
> （找 `Application_Start` 之后创建 0x2ca/count44 的那个调用）。

### 2.2 显示消费容器 `HOSDAP02`
```c
#define HOSD_CONTROL 0x8280074d   /* 控制 */
#define HOSD_UPDATE  0x8280084d   /* 像素更新（1002→1003/1005 配对） */
#define HOSD_META_UPDATE 0x8280084e
#define HOSD_AP      0x8288076c   /* AP 表面 */
#define HOSD_GUI     0x9088076b
#define HOSD_PIXELS  (640*480*2)  /* RGBA4444 */
#define HOSD_HEADER  128
/* 容器 = header(128) + metadata(gui[80]+widgets[256][96]+extra[16]+present[258]) + pixels */
```
**⇒ 这解释了他们的帧格式：640×480 RGBA4444，带 128 字节头和元数据。
   我们的 `/dev/streamfb format=1` 悬案，很可能就是同一族格式。**

### 2.3 输入键码（第 8 步，先记着）
```
MENU 0x1ab   确认 0x1ac   上 0x3   下 0x30   左 0x15   右 0x1af
删除/C2 0x1f8    右后拨盘 0x10000013（单发 status=-1024/+1024）
协议：按下=1、释放=0，guest 侧 50ms 短按
```

### 2.4 实现文件清单（都在 `runtime/analysis/`）
| 文件 | 行数 | 作用 |
|---|---|---|
| `menu-observe.c` | 3,159 | 用户态注入库：hook `uxengine_init2`/`application_init`/dlsym/dlopen，替身服务 |
| `headless-osd.c` / `.h` | 326 | **AP-only 软件消费端**：帧 gate、位图锁、HOSDAP02 提交 |
| `sony-lz77.c` / `.h` | 72 | **同格式 CPU LZ77 解码器**（替代 `/dev/ldec`） |
| `ramfb-viewer.c` | 305 | 读已提交容器 → 校验 → 转 XRGB8888 → 写 ramfb |
| `qemu-menu-probe.py` / `run-menu-probe.sh` | — | 启动与取证 |

## 3. 黑屏分类表（他们踩过的坑，我们直接受益）

| 看到什么 | 先查什么 | **不能**得出什么结论 |
|---|---|---|
| 无画面，串口停在早期 | Image/DTB/initrd 地址、bootargs、timer/IRQ | 不能说 UI 资源缺失 |
| appFw 已跑、启动控件在，只收到**清屏** | 原生命周期、控件内容、`notifyDraw`/`drawFramebuffer` 是否真被调用 | 不能说"屏已建所以菜单已画好" |
| **离屏有菜单，第二帧不返回** | 输出接收者、帧 gate、缓冲租期与消费通知 | 不能只发空 ACK 宣称显示恢复 |
| AP 已提交，QEMU 窗口仍黑 | 构建是否有 GTK/SDL、是否真配 ramfb、显示设备是否接到该帧 | 不能把原生窗口与 Sony 显示协议当同一件事 |

**⇒ 第 3 行正是我们的处境：我们的"引擎提交了 19 个栅栏包"很像"离屏有东西但第二帧不返回"。**

## 4. 对我们路线的判断

### 4.1 他们成功的本质
```
不建模硬件 ⇒ 用 LD_PRELOAD 注入用户态库，把 GPU/CP/LIRO 的"缺席"用软件替身补上
```
**⇒ 这解释了他们为什么能出画面而我们卡在设备模型：我们的努力方向是**反的**。**

### 4.2 我们能不能照搬？
**不能直接照搬，但方法论可以迁移。** 障碍：

| 障碍 | 说明 |
|---|---|
| 机型不同 | 地址（如 `0x1e78870`）、键码、控制器编号都是 A7C II 的 |
| 引擎不同 | 他们是单层（`libObj` 导出 `Application_System_Init`）；ZV-1M2 是两层（`appFwBoot`→`appFw`→`Application_Start`） |
| 我们的更早期 | 我们连 backup 队列接收者都没有，他们已经有完整替身服务集 |

### 4.3 建议的迁移顺序
```
① 先解决 backup 0x3e014d 无接收者（否则 ^C 之前的一切替身都无从谈起）
② 套用他们第 5 步：给 /dev/ldec 写 CPU LZ77 解码（我们树里 ldec 节点已建但无驱动）
③ 套用他们第 3 步：找到我们这代的"菜单 controller 创建入口"，主动调用
④ 套用他们第 6 步：AP-only 软件消费端，把"等 sugilite 完成位"整条跳过
⑤ 套用他们第 7 步：ramfb（我们的 QEMU 是自建的，加 fw_cfg ramfb 不难）
```
