# 真机 Backup.bin 实测结果 —— 对本 PR 早期结论的重要更正

> 2026-10-27。我们的团队从真实 ZV-E10 采到了 `/setting/Backup.bin`
> （1,235,740 B，pmca 服务模式只读 pull），并完整解析。
>
> **结论：本 PR 早期版本里的两个「绕过」补丁，建立在错误的合成数据上。
> 如果你也在用合成的 backup DB，请先看这一份。**

---

## 1. 真实布局（会推翻很多猜测）

```
+0x000   头部（0x100 字节）
+0x100   页表 819 项 × 6B { u16 count, u32 cum_base }
+0x1432  槽表 33178 项 × 6B { u16 ?, u32 v }
+0x31DCE 槽表结束（第一条记录的 payload 在 0x31E04，中间 54 B 填充）
```

- 用 **PT = 0x100** 时，819 项 `cum_base` 链完全连续
- 用 PT = 0x10C 会在第 817 页断链（`cum` 变成 67313124 这种荒谬值）
- **186 个非空页**，槽总数 **33178**
- 槽值 `v = (type << 24) | 绝对文件偏移`
  - `type` = 记录长度（1 / 4 / 28 / 64 / 2040 …）
  - `type == 0xFF` = 间接长度：**off 处读 u16 长度，payload 在 off + 2**

## 2. ★ 四处硬错误（如果你也合成过 DB，很可能全中）

| id | 常见合成写法 | **真机实际** | 后果 |
|---|---|---|---|
| `0x00810000` | 28 B 路径字符串 | **64 B**（路径 + 36 个 `0x00` 补齐） | 强制 `size=28` 会让长度语义错位 |
| `0x01120001` | 28 B 四 magic，count 填 0 | **2040 B**，内含 `count_A=15` / `count_B=11` | 强制 count=0 等于抹掉真实结构 |
| `0x00FA0028` | `0x8F000000` | **`0x20098000`** | MonDrv FixedArea 地址错 |
| `0x00FA005D` | `0x00080000` | **`0x0007C000`** | 同上 |

### 2.1 BIN! 记录的真实形状

```
42 49 4e 21   BIN!
48 03 00 00   0x348  (=840)
0f 00 00 00   15
0b 00 00 00   11
43 4e 46 21   CNF!
6a 00 00 00   106
3d 00 00 00   61
...
（共 2040 字节）
```

**15 / 11 这两个数，正好能解释装载器里 `new[](count_A * 16)` / `new[](count_B * 52)` 的乘数。**
我们之前硬把它们清零，等于让装载器走空列表路径——**这就是为什么需要「绕过 CNF!/PTN! 检查」。**

### 2.2 fontlist 记录

```
0x00810000 → type=64, 内容 "/usr/share/app/fontlist.dat" + 36×0x00
```

真机长度 64，不是 28。

## 3. 对上游的两个直接建议

### 3.1 不要再用「绕过 magic 检查」

本 PR 里的 `patch_libobj_discrim.py` / `patch_libobj_bypass_cnf.py` 是**诊断工具**，
不是修复方案。它们的价值在于「后移崩点、方便排查下游」，
但如果能得到真机 DB，**装载器会自然通过三道检查**，不需要 NOP 任何东西。

我们正在往这个方向走（真机 DB 已装入 QEMU，DB 通路验证打通：
运行前后只差 1 字节，`+0x00` 保持在 `0x20001000`）。

### 3.2 如果拿不到真机，至少把合成值改对

不可能完全对齐（33178 个槽位没法造），但**这四处必须对齐**，否则会一直在
「绕过 → 下游崩 → 再绕过」的循环里：

```
0x00810000 : 64 字节，路径 + 补 0
0x01120001 : 至少把头部的 0x348 / 15 / 11 写对
0x00FA0028 : 0x20098000
0x00FA005D : 0x0007C000
```

## 4. 关于内存落点（真机 DB 是 1.2 MB，会撞 WBI）

真机 DB 1.2 MB，比合成的 30 KB 大 40 倍，会撞上 `cxd90045_wbi_segs` 的段。

**实测：内核（backup.ko）会把 DB 头 `+0x00` 强制写回 `0x20001000`**（硬编码默认值）。
所以 **DB 不能挪**——我们试过放 `0x24000000`，运行时被打回 `0x20001000`。

正确做法是**把 WBI 前三段腾开**：

```c
// 原：
{ 0x001000, 0x20021000 }, { 0x0EC000, 0x20028000 }, { 0x008000, 0x20145000 },
// 挪到（WBI 段7 结束 0x24000000 之后、KLOG 0x30000000 之前）：
{ 0x001000, 0x25000000 }, { 0x0EC000, 0x25001000 }, { 0x008000, 0x250ED000 },
```

腾出 `0x20001000-0x2014D000`（约 1.33 MB），1.2 MB 的真机 DB 放得下。

工具：`contrib/tools/free_lowmem_for_db.py`（如果有需要可以加进来）

## 5. 采集方法（如果你也想拿真机数据）

只读、不改相机：**pmca 服务模式 `pull /setting/Backup.bin`**。

- 环境：一台能插 USB 的电脑 + Python 3.8+ + pyusb
- Windows 需要 Zadig 装 **WinUSB** 驱动（`libusb_package` 自带 `libusb-1.0.dll`，不用另找）
- 切服务模式时相机会重新枚举，Windows 上可能要**再装一次**驱动
- 命令：`python3 pmca-console.py serviceshell` → `pull /setting/Backup.bin`
- 文件约 1.18 MiB，完整 pull 一次即可

我们做了一个自包含的工具包（含 pmca + libusb DLL + 一键脚本 + 排错表），
如果需要可以一并贡献上来。
