# 交接：ZV-1F 新菜单在自研 QEMU 里"启动 6 秒后永久冻结"的完整定位

> **日期**：2026-10-28

## 0. 一句话结论

App（`im.real` + `appFw.so`）在 QEMU 里零崩溃启动，**6 秒后 105 个线程全部睡死**。
根因已定位到最底层：**App 向 uipc 队列 `0x8F013A` 发了 2425 次请求，
却只在应答队列 `0x8F0139` 上等到 72 次回复（3%），然后用无限超时永久等待**。
不是线程饥饿、不是内存不足、不是缺模块、不是注册被拒。

**建议停手**，理由见 §6。如果要继续，唯一有价值的路见 §7。

## 0.5 ★ 下午增量（17:00–19:10）：SKIPDMP 绕过第一道门 + 探针 v2 上线

### 0.5.1 `SKIPDMP=1` 绕过 `dmp_allocator` 断言

`dmp_allocator_lib_init` 的 `MA_ErrNone` 断言是第一道门。用 `patch_libobj_skipdmp.py`
把 `grm_init` 里的 `bl DMP_2D_Initialize` NOP 掉后：
- `app.err` 从 116 B（断言崩溃）变成 54 B（正常输出 `DMP_2D_Initialize : 1`，NOP 后的垃圾返回值）
- App 进入库加载阶段：T+2s 仅 1 线程 / 1.9 MB RSS → T+26s 9 线程 / 14.4 MB RSS
- **但 `appFw.so` 始终没被 QMP 扫描器找到**（400 秒 / 75 轮全 MISS）

### 0.5.2 探针 v2（`core-sync-trace-v2.c`）

- 加 **TID**（`gettid=224`）、**CLOCK_MONOTONIC 微秒时间戳**（`clock_gettime=263`）
- 加 **run-id**、逐次 **qid**、cmd 7 的 **timeout**、**TRUNC** 标记
- **`SYS_clock_gettime` / `SYS_gettid` 宏展开为空**（交叉工具链 `<sys/syscall.h>` 宏链断裂）
  ⇒ 必须硬编码 ARM EABI 号：`write=4 ioctl=54 open=5 readlink=85 gettid=224 clock_gettime=263`
- 本轮实测 **1447 行 trace / 49 KB**，App 在跟 `0x8F013A`（日志服务）和 `0x3E014D`（backup）活跃通信

### 0.5.3 观察者存活问题

`( ... ) &` 子 shell 在 `exec im.real` 后被杀（只抓到 T+2s）。
`trap '' HUP` / `setsid` / `disown` 均不完全可靠。
**最终方案**：把 `dump_all` 合并进 `dm.sh`（与 maps 序列共用一个脚本），用 `&` + `disown` 启动。
实测能抓到 2 次心跳（T+18.65s / T+26.59s），之后仍被杀 —— **FAT 写入可能太慢**。

### 0.5.4 `best3` 模式对照（推翻"objset 补丁致崩"假设）

| 模式 | libObj 补丁 | backup.ko 补丁 | input.ko | App 表现 |
|---|---|---|---|---|
| `objset` | ✅ 3 个 | ❌ | 保留 | 加载 appFw → 崩在 dmp_allocator |
| `best3` | ❌ | ✅ 2 个 | **删除** | **41 轮全 MISS，appFw 根本没加载** |
| `objset+SKIPDMP` | ✅ | ❌ | 保留 | 过 dmp_allocator → 库加载中（9 线程） |

⇒ **`objset` 的 libObj 补丁是必要的**，没有它 App 更早就死。

## 2. App 的 IPC 全貌（实测）

用 `LD_PRELOAD` 探针（`core-sync-trace.c`）拦截 `ioctl`，只记录 fd 指向 `/dev/uipc` 的调用。
给每次调用打 **全局序号**，REQ/RET 共享同一 seq，配对无歧义。

全量 **11389 次调用**：

| cmd | 语义（反汇编得到） | 次数 | 真失败(-1) |
|---|---|---:|---:|
| 0 | `__k_4u_stat_sem` | 0 | — |
| 1 | `__k_4u_wai_sem_tmo` | 423 | 0 |
| 2 | `__k_4u_sig_sem` | 423 | 0 |
| 3 | `__k_4u_stat_msgq` | 7 | 0 |
| 4 | `__k_4u_snd_msg` | 2177 | 0 |
| 5 | `__k_4u_snd_sync_msg` | 1176 | 4（1020） |
| 6 | `__k_4u_snd_sync_direct` | 2202 | 0 |
| **7** | **`__k_4u_rcv_msg_tmo`** | **72** | **3（1022）+ 34 次永不返回** |
| 8 | `__k_4u_reg_msg_queue_cb` | 114 | 0 |
| 9 | `__k_4u_unreg_msg_queue_cb` | 4 | 0 |
| 10 | `__k_4u_valloc_msg_wait` | 3334 | 0 |
| 11 | `__k_4u_free_msg` | 1193 | 0 |
| 12 | `__k_4u_dynamic_id` | 231 | 0 |
| 13 | `__k_4u_wait_cb` | 33 | 0 + 4 次永不返回 |
| 14/15 | `__k_4u_set_msgq_b…` / `l…` | 0 | — |
| 16 | `__k_4u_connect` | 0 | — |

**关键**：真实失败率几乎为 0。**卡死不是"返回错误"，是"永不返回"。**

### 2.1 cmd 7 的确切语义（反汇编 `osal_uipc.ko`）

```
__k_4u_rcv_msg_tmo(a0=qid, a1=用户指针, ctx):
    copy_from_user(local, a1, 8)          ; {void *buf; u32 timeout;}
    osal_rcv_msg_tmo(qid, &msg, timeout)  ; 阻塞收
    若成功: copy_to_user(buf, msg, 4)
```

`osal_rcv_msg_tmo`（0x34ec）内部：
- `uxth r7, r0` ⇒ **qid 被截断成低 16 位**
- 队列找不到 ⇒ **返回错误（不阻塞）**
- 队列找到但链表空 ⇒ **睡在等待里**，超时用 `timeout+1 > 上限` 判断

我们的 arg 结构：

```
+00 0x8f0139    → qid
+04 0x5b2aca0   → 指向 +08
+08 0x5b2ad84   → buf（应答会 copy_to_user 到这里）
+0c 0xffffffff  → timeout = -1 = 无限  ★
```

⇒ **34 个线程就是 34 次"无限期收 0x139 的消息"，而消息永远不来。**

## 3. ★ 核心发现：`13A → 139` 是配对的一对队列

给探针加「记录 cmd 4/5 的目标 qid」后，全量 3353 次发送：

```
0x8f013a   2425 次   ← App 主要发往这里（请求队列）
0x3e014d    753 次   （backup 服务）
0x14c0424    79 次
其余零散            （0x8f0139 只被"发送"过 1 次）
```

而 App 在 `0x8f0139` 上**收**：72 次调用，38 次拿到，**34 次永挂**。

`/proc/osal/uipc` 里两个队列都在：

```
LMSGQ:          139  0 1 1 0 1 0 0 0      ← 第二列 = 1
                13A  0 2 1 0 1 0 0 0      ← 第二列 = 2（监听者更多）
vblock:  139(192)    ac400020  8192        ← 小块
         13A(19328)  ac402020  81920       ← 大块
```

⇒ **13A = 请求队列（大块），139 = 应答队列（小块）**，相邻编号、配对使用。
**App 发 2425 次请求，只等到 72 次应答 —— 应答率约 3%。**

### 3.1 这意味着什么

- **不是"缺 CP 硬件"**：队列存在、有监听者、请求"发送成功"（ret=0），说明 uipc 通路是活的。
- **是"请求处理器收到但不回"**：应答队列几乎永远是空的。

### 3.2 已排除的生产者候选

| 文件 | 对 `0x8f0139` 的用法 | 判断 |
|---|---|---|
| `osal_ulogio.ko` | `ulogio_unreg_listener` 里 unreg/清理 `0x8f0313 / 0x8f0139 / 0x8f013a` | **订阅方**，不是生产者 |
| `backup.ko` / `dmm.ko` | 成对 `ldr` + 查表形态，不是"发送消息" | 排除 |

`osal_ulogio` 的 `refcnt=0` 属正常（被用户态使用不增 refcnt）。

## 4. 反汇编速查：`osal_uipc.ko` 的 ioctl 结构

**ioctl 入口 `__k_uipc_cdev_ioctl @ 0x5a8`**：

```
5bc: ldr r6, [r1]                    ; cmd
5c0: ldr r1, [r1, #4]                ; 用户 arg 指针
5ec: copy_from_user(fp-0x24, r1, 8)  ; ★ 只拷 8 字节（两个 u32）
614: bic r6, r6, #0x80000000         ; 清方向位 ⇒ cmd = 低值
618: cmp r6, #16 / bgt               ; cmd 范围 0..16
64c: cmp [ctx+16], current->pid      ; 非同进程 → printk "called from different process"
66c: ldr r3, [pc,#44]                ; = .rodata 基址（重定位 0x6a0 → .rodata+0）
678: add r6, r3, r6, lsl #2
680: ldr r3, [r6, #40]               ; 表项 = .rodata + 0x28 + cmd*4
684: blx r3                          ; handler(a0, a1, ctx)
```

**跳转表** = `.rodata + 0x28`，17 项，来自 `.rel.rodata`：
`stat_sem / wai_sem_tmo / sig_sem / stat_msgq / snd_msg / snd_sync_msg / snd_sync_direct /
rcv_msg_tmo / reg_msg_queue_cb / unreg_msg_queue_cb / valloc_msg_wait / free_msg /
dynamic_id / wait_cb / set_msgq_b… / set_msgq_l… / connect`

> 复现方法：`arm-linux-gnueabi-readelf -r osal_uipc.ko | sed -n '/rel.rodata/,/^$/p'`

## 5. 工具与复现

### 5.1 探针（`core-sync-trace.c`）

**一个库干两件事**：①补 `libCoreSync` 的 3 个 stub 符号（`core_sync_user_init/sus/res`）
②拦截 `ioctl`。这样只占**一个** preload 槽（已知：两个 preload 库会让 App 卡住）。

```bash
arm-linux-gnueabi-gcc -shared -fPIC -O2 -march=armv7-a -mfloat-abi=softfp \
  -fno-builtin -DFAKE7_COUNT=0 -o libCoreSync_trace.so core-sync-trace.c
```

编译期开关：
- `-DFAKE7_COUNT=N`：伪造前 N 次 cmd 7 直接返回 0（实测：App 行为无变化，因为应答要写 buf）
- `-DDUMPBUF=0/1`：dump cmd 7 结构的前后内容
- `-DDUMPQID=0/1`：记录 cmd 4/5 的目标 qid

**三个必须知道的坑**：

1. **日志必须写 `/tmp`（ramdisk），不能写 `/setting`（FAT）**。
   否则 6963 次 ioctl × 2 次 write 会把 App 从 50 秒拖到 133 秒，根本跑不到卡点。
2. **不要在库初始化时调 `getenv`**：实测让 `im.real` 在 exec 后立刻进 `D`(disk sleep)、
   只剩 8 线程、VmRMS 2 MB、239 秒加载不出 appFw。改用**编译期宏**。
3. **`errno` 在成功时不会清零** ⇒ 只有 `ret == -1` 的 errno 才有意义。
   早期用 `ret=0` 记录的 errno 全是残留，会得出完全错误的"错误率"结论。

### 5.2 读内核日志（`run-klog.sh`）

cmdline 的 `klog.addr=0x30000000 klog.size=...` ⇒ printk 被重定向到物理内存。
用 QMP `human-monitor-command pmemsave 0x30000000 <size> "/tmp/klog.bin"` 直接读。

**三个坑**：

1. **`loglevel=3` 会把 klog 清空**（实测只剩 4 个非零字节）—— 别用。
2. **默认 1 MB 会被 eMMC tuning 警告冲满**：`AL_EMMC_SEQ (execute_tuning)` 每 1–2 ms 一条
   `Warning : Software Tuning is forbiden for non-HS200 mode`，9118/9120 行都是它，
   1 MB 只够存 18 秒 ⇒ App 启动那 6 秒必被冲掉。
3. **`klog.size` 改 `0x00800000`（8 MB）就够**：非 tuning 有效行 142 行，不再绕回。

**结果**：有效日志止于 `0.526142 hwtimer cpu2 OK`，0.5 秒之后内核几乎不输出
（连 insmod 都没有）⇒ **klog 里不存在 UIPC / ulogio 的错误信息**。

顺带确认：`[0.416706] Brought up 1 CPUs` ⇒ **上游那条 `-smp 2` 经验在本机型不可能实现**
（除非改内核平台代码）。

### 5.3 断点与寄存器 dump（`bf-dump.gdb`）

`get_boot_factor`（`appFw.so` 偏移 `0x172a1ac`）相关断点，命中时打印 r0–r15 + fp 链 + 栈扫描。

**注意**：`appFw.so` 是 stripped 且**不用标准 ARM frame pointer 链**，扫栈找返回地址不可靠
（抓到的地址反汇编验证不成立）。这条路走不通，别浪费时间。

## 6. 为什么建议停手

按预设止损判据（klog 干净 ⇒ 处理器收到但不回 ⇒ 成本不可控），条件已满足。
但**如实说明其局限**：klog 干净可能只是因为该内核抑制了 0.5 秒后的 printk，
不等于"没有错误"。所以停手的真正理由是**投入产出比**：

- 要让 App 继续，必须让**请求处理器真正回复** —— 这需要再逆向一层 ulogio 请求协议
  （消息格式、日志设备、可能的用户态配合），属**新项目级投入**。
- 过了这关后面还有：显示初始化（DMP/GLES/GPE）→ uxengine → 资源加载 → 视图层。
- **新菜单在 QEMU 里从未被任何人跑通过**（同 SoC 的 ZV-E10 老菜单有人跑通，但那是 `libObj` 单体架构，
  不经过 `appFwBoot → appFw.so` 这条链）。

## 7. 如果要继续，唯一值得走的路

**不要再往下伪造 uipc。** 最省力的路是：

**把这份依赖图交给有真机的团队** —— 用同一个探针（改一下编译参数就能用）在**真机**上抓一次
`0x8F0139` 的应答长什么样。一次采样就能省掉 QEMU 侧几天的猜测。

QEMU 这条线的真正价值是**安全沙盒**：能做真机上不敢做的实验（改库、patch `.ko`、伪造消息）。
它的使命是**理解需求**，而不是必须画出画面。
