## 九、★★★ 根因确定（23:40 更新）

### 精确时间线

```text
23:33:20  wpa_supplicant: AP-STA-DISCONNECTED 7c:b8:da:ee:91:05
          ← 相机从 AP 断开，此后再无任何 DHCP 请求
```

**这正是我 `kill -15 149`（杀 bootin）+ 手动跑 `bootin.elf` 的时刻。**

### 根因：`menu_ui.so` 的构造函数里有 `sleep(10)`

```c
menu_ui.c:121    sleep(10);      // 等 UI 线程起来
```

**致命链条：**

```text
1. LD_PRELOAD 的 constructor 在 **im.elf 进程启动的最初阶段**执行
   （在 main() 之前，在 UI 初始化之前）
2. sleep(10) 把 im.elf 的启动**阻塞 10 秒**
3. 相机 watchdog（wdt.timeout=500，即 500 个 tick）判 im.elf 启动失败
4. 重启 → 但 **dmode="3p" 和 preload 是持久化在 /setting 的**
5. 重启后又加载 menu_ui.so → 又阻塞 10 秒 → **启动循环**
6. 循环中 Wi-Fi 永远来不及起来 ⇒ 我彻底失联
```

**对照：之前成功的 `nm_probe3.so` 没有任何 sleep，只写一行日志立刻返回 ⇒ 零阻塞。**

### 这是我的严重设计错误

```text
✗ 我在构造函数里 sleep
✗ 我把"等 UI 起来"这种逻辑放进了一个会阻塞整个进程启动的地方
✗ 而且它还是持久化加载的（dmode=3p 写在 /setting 里）

✓ 正确做法应该是：
  构造函数里只做"注册一个回调"或"fork 一个子进程"，立刻返回
  绝不能在前台阻塞
```

## 十、恢复方案（需要用户配合）

```text
相机现在很可能是「启动循环」状态：
  dmode=3p + preload→menu_ui.so（带 sleep(10)）⇒ im.elf 启动永远超时

⇒ 必须让相机能够读到「dmode=3」才能恢复
⇒ 但 /setting 是相机自己的分区，我们无法从外部改
⇒ 除非：
   a) 拔电池后仍能进某个恢复模式
   b) 有 USB 连接 + PMCA/bk.elf 之类的工具能改 /setting
   c) Pico fastboot 直接写 /setting 分区
```

**⇒ 最可行的是 (b)：用 USB 连电脑，如果能进 USB 服务模式（相机有 USB 相关服务），
   可以用 bk.elf 改 dmode。但相机现在连 Wi-Fi 都起不来，USB 模式未必能进。**

**⇒ 或者 (a)：取出电池再装回，看看是否有一个"安全启动"路径（比如 bootin 的 non-p 模式）**
